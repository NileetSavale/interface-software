# Decision log

Where the AI assistant proposed one thing and I (the author) chose differently, or changed its mind because of my
pushback. Recorded so the reasoning, not just the outcome, survives into REPORT.md and review.

| # | Topic | AI proposed | I chose | Why |
|---|---|---|---|---|
| D1 | Irreversible actions | Allow them with human approval through the handoff channel | **Block entirely**; the schema rejects irreversible steps | This layer is the agent's hands, not its judgment. Whether to commit a money-moving change belongs to the agent product plus a human. "No artifact can ever contain a commit" is simple to audit and test. The brief's example only asks to *reach* the confirmation screen. |
| D2 | Screenshot policy | Tree only; a screenshot when the tree is thin, an action changes nothing, or the model asks | **Screenshot + tree on the first visit to a screen state; tree only on later visits**, plus the AI's triggers | The model needs the full picture once per unfamiliar screen. After that, the tree is enough and costs less. Page fingerprints make "first visit" detectable. |
| D3 | Shared app knowledge | Not proposed | **A page map:** a weighted graph of screens and actions that grows with use (my idea) | Every operator at a bank uses the same app, so what one run learns should help the next. Discovery gets cheaper and drift becomes visible. |
| D4 | Page map scope | Local map built, sharing designed only (to avoid "premature infrastructure") | **Build it fully** (as a library, not a service) | It's the mechanism behind cheaper discovery, drift detection and the replay fallback. Built as an embedded per-bank store with no server, and justified by a measured result. |
| D5 | Page map sharing | Two layers: a vendor-product base plus a per-bank layer | **Per-bank only** | Maps are learned automatically and nobody reviews each entry, so they stay inside the bank that produced them. Artifacts can still be shared per vendor product because they're curated (human-approved). |
| D6 | Map in replay | The map never influences replay (AI argued it breaks determinism) | **A bounded map-assisted fallback** with guardrails. *The AI changed its mind.* | Pinning the map version keeps replay deterministic and auditable. Requiring the fallback to reach the step's declared `expect` state means the artifact still decides *where* replay ends up. Read-only edges when unattended. The fix is fed back as a proposed override, so a human reviews it. |
| D7 | Page map write rules | Three strict rules (verified runs only, weight by source, no edges into error states) | **Agreed** | The map can now steer replay through the fallback, so a poisoned edge would spread to every operator at the bank. Slower learning is the accepted cost. |
| D8 | Override addressing | JSON Patch by array index (the AI's own example, a flaw it raised itself) | **Step ids + a semver `appliesTo` range** | Index paths silently shift when a step is added, so an override can rename the wrong control: the same failure as the nth-index rule I rejected. Ids fail loudly. The semver range lets overrides survive non-breaking base updates across hundreds of banks. |
| D9 | Control-transfer mechanism | A "lease" (holder + epoch + expiry), described in distributed-systems terms | **Same mechanics, named a "control token" and explained plainly** | The epoch fixes a real race even in one process (an async click still running when control passes to the human), and expiry fixes the operator who walks away. The brief penalizes premature infrastructure, so it's framed as the small mechanism it is. |
| D10 | Build order | Replay first, tested with a hand-written artifact; discovery and recorder last | **Full schema first, then a thin end-to-end slice, then deepen** | A hand-written artifact is idealized, and the recorder (turning a live click into a robust descriptor) is the hardest code. Replay-first finds that out last. The brief prefers thin-but-real across the whole thread, and the real discovery run is the biggest risk. Writing the schema first keeps the contract from being shaped by the crude recorder. |
| D11 | Invocation when replay pauses | (not designed; raised as a challenge) | **Sync with a deadline, falling back to a run handle; late results kept for a 15-minute TTL** | The calling agent is usually in a live conversation. Blocking for a 10-minute handoff times it out, and aborting wastes the human's work. A deadline feels synchronous in the common case. The TTL and `completedAt` stop stale answers from being delivered silently. |
| D12 | Discovery model | Sonnet 5.5, chosen without being challenged | **Sonnet → Opus when stuck → human** | Discovery's cost is spread over every LLM-free replay, so first-try success matters more than token price, and operator time costs far more than tokens. Sonnet keeps the common case fast and cheap; Opus is a cheaper rung than a human handoff. |
| D13 | Language | TypeScript + Playwright (locked before loop_runner was shared); the AI then recommended switching | **Python 3.13 + Playwright, Pydantic, FastAPI** | loop_runner's tool-use loop, caching, history policy, redaction and token accounting are already built and measured in Python, and I can defend Python code line by line. The job posting names no stack. Nothing is lost technically. |
| D14 | Evaluation harness | (missing from the design) The AI then recommended deterministic suites in full and discovery at small N | **The full harness: all five suites at meaningful N**, with a hard USD budget cap | The job posting is explicit: "Vibes don't pass review; evals do." Evals are the core of the role, and loop_runner's research log shows I already work this way. The budget cap and stated N keep the spend bounded and the numbers honest. |
| D15 | Overall scope | The AI pushed back: several "build fully" choices add up to a scope that may read as not making cuts | **Cut the capability catalog; a ~5-day time-box with a priority order (drop from the bottom)** | The brief grades judgment and cut lines, not endurance. A fixed priority order means anything unfinished is the least important work, never half of the core. |
| D16 | Masked PII vs. finding the right record | The AI raised the problem itself (with masked rows, the model can't tell which member is 12345) and recommended input-match markers | **Input-match markers + last-4 on other identifiers; a mandatory identity checkpoint (`WRONG_RECORD`, fatal)** | A wrong member's balance returned as success is a data exposure. Markers tell the model which row matches without sending the number to a third party, and last-4 follows bank-statement convention. The in-process identity check means correctness never depends on the model having seen the value. |
| D17 | How old snapshots leave the context | Collapse old snapshots to one line in our own message history (the AI's original history policy) | **Server-side context editing (`clear_tool_uses`); the history stays append-only.** *The AI corrected its own locked proposal.* | Found while reading the current API docs in Pass 1: Sonnet 5.5 and Opus 5.5 bind their thinking to the exact conversation, so a client-side edit of an earlier message invalidates it (an HTTP 400 for new accounts). Server-side clearing doesn't count as an edit and achieves the same goal. It's the mechanism loop_runner already used. |
| D18 | Where flow-specific business outcomes come from | The reviewer writes them by hand at approval (D-locked in §3). The AI then recommended probes | **Probes + review.** The goal lists probe inputs; after recording, the artifact is replayed with each (no LLM), the model names the screen where it stopped, and the outcome is kept only if it proves itself | Hand-written regexes make every discovered artifact incomplete until a human is an expert in its detectors. A probe costs one short model call and is verified by construction: the probe must now end in the outcome, and the discovery inputs must still succeed. The human still approves. |
| D19 | Handling a wrong record | Check identity at the end-of-run checkpoint, return `WRONG_RECORD` with last-4 and a screenshot. The AI then flagged three weaknesses in its own design | **Identity gate before any read or act; structure-only evidence and no screenshot; nothing about the other record goes to the caller; an audit log and a circuit breaker that needs re-approval** | The end-of-run check came after the other member's data had been read, and for a write flow after it had been acted on. The failure evidence stored a third person's PII. Treating a repeat as an incident (the capability stops running unattended) is what a bank would expect when an app starts serving the wrong records. |
| D20 | Guards a hostile page can't talk its way past | (found by the safety eval, Pass 2 item 5) The design relied on the button-name classifier, with a mislabelled "OK" listed as residual risk | **The AI's change, open for review: a network-level gate (origin allowlist on every request; allowed paths and declared `commitPaths` on every page load or post), credentials typed only on the sign-on page, and outcome checks on the screen where a control is found** | The eval showed each gap concretely. A tampered artifact pressed "OK" on the review screen; only the browser closing at the end of the run kept the account from opening. A link took the browser off-site. Discovery would type the password into a fake re-login form. A guard below the page holds whatever the page says. **Then, from the Claude safety cases:** Claude was refused the password 3/3 times but pressed the fake form's Verify anyway, and the click was recorded. The AI offered prompt-only, review-flag-only, or all three of form block + review flag + prompt line; **the user chose all three (option A).** |
| D21 | Surviving a tenant's relabel | (Pass 2 item 6) The locked demo needed "a fallback hits" when a button is renamed, but every recorded strategy keyed on the name | **The AI's addition, open for review: an `onlyInRegion` strategy ("the only button in the Member Inquiry fieldset"), recorded only under a labelled region scope and only when unique; refused by the schema without a region** | Relabels are the commonest difference between banks on one product, and role, label and text strategies all fail together on one. Position within a named region survives a rename. It still never guesses (two matches fail), and the live policy re-check and network gate still apply. The drift it reports turns into a proposed override, so the name-based strategy is restored after review. |
| D22 | Stable outcome codes | (found by the discovery eval) Probes let the model name each outcome freely; the same screen came back as `DEPOSIT_BELOW_MINIMUM` and `MINIMUM_DEPOSIT_NOT_MET` in different runs. The AI recommended that probes name the code they expect | **Agreed: each probe in the goal spec says the code it expects; the model must use it or say none fits** | A caller branches on the code, so a re-discovery that renames it is a breaking change nobody asked for. The goal author owns the vocabulary; the model only recognises the screen. The same mechanism closed the cross-flow gap: the sub-account goal probes a missing member too and learns `MEMBER_NOT_FOUND` under the same code as lookup. |
| D23 | When a postcondition carries another bank's label | (found building the page map, Pass 2 item 7) Sign-on is proved by the next step's control, so a bank that renames that control fails sign-on, and the "already signed in?" check misreads after a re-sign-on | **The AI's addition, open for review: the page map may confirm a postcondition or the precondition check, but only exactly: the screen now showing must be where this same action is known, from trusted edges, to lead on this bank. Reported as `MAP_FALLBACK` with the pinned map version** | The check still asks "did we reach the right screen?", answered from the bank's own verified history instead of another bank's label. It's deterministic for a given map version, and it adds no way through that a verified run on that bank hasn't already taken. |
| D24 | Names that only free text mentions | (the one known gap in the safety eval) The AI offered a fail-closed rule, a spaCy NER model, or both, and recommended the rule | **The rule: in prose only, hide every run of two or more capitalised words, or a title and a name, unless the page uses it as a label** | A bank needs a guarantee, not a probability. The rule is deterministic, adds no dependency, and errs toward hiding: at worst a phrase that isn't a name is hidden. A statistical model catches lone first names but can miss names outright, and it ties what the model sees to a model version. Lone first names stay a stated limit. |
| D25 | Who may use the operator page | (found listing gaps before submission) The page had no check at all: anyone who could reach the port could see the live, unmasked screen and take control or abort, the index listed every intervention, and any site in the operator's browser could post to it. The AI recommended a per-intervention key | **Agreed: a random key per intervention, delivered only in the printed link's `#` fragment and required as a header on every call; an empty page shell; Host, framing and caching locked down; refusals logged** | Taking control of a live banking session is the most powerful action in the system, so it has to be the hardest to reach. A header can't be forged cross-site without CORS, the fragment keeps the key out of every log, and the key is scoped to one intervention and dies with it. Identity stays self-declared: that belongs to the bank's sign-on, not to this layer. |
| D26 | Whose credentials a tenant's replay types | (found listing gaps before submission) Every bank's replay read the same `APP_USER` from the environment. The AI recommended a per-tenant lookup behind a mapping, with no fallback | **Agreed: `{{secrets.APP_USER}}` on bank B is `APP_USER__B` and nothing else; a missing one fails before the browser opens (`MISSING_SECRET`), naming the key and never a value. The source is any mapping, the environment by default** | A fallback to the shared name is exactly how one bank's operator would be signed into another bank's system. Failing loudly at preflight beats failing at sign-on with a half-run. Reading secrets through a mapping means a vault client drops in without touching replay. |
| D27 | Reading the first row of a results list | (found on ParaBank) "The first transaction found" has nothing stable to name its row by: the row's key is a date, which is data. The only way to say it is a position, which my D8 rule rejected for picking controls. The AI offered a narrow `row: first`, matching by amount, folding it into item 5, or dropping the flow | **A narrow `row: first` on a table cell: reading only, never acting; recorded only when the goal declares it wants the first result; on a table found by its own label and header; an empty table finds nothing** | D8 is about choosing between same-named controls, where an index silently picks the wrong one. "The first result" is what the caller asked for, so the position is the meaning, not a guess. Keeping it off controls means nothing is ever clicked by position, and an empty table failing is what turns "no transactions" from a hollow success into an answer. |
| D28 | Results that span pages | (Pass 3 item 5) An artifact was a straight list of steps, so a row on page 3 couldn't be reached by a capability recorded with the row on page 1, and "press Next" recorded twice only works when the row is on page 3. The AI recommended one bounded loop, or none | **A `pageUntil` step, the only loop an artifact can hold: press the Next control until `until` (the row the next step uses) finds exactly one element, at most `maxPages` times. Recorded only from the model's `next_page` tool, which is offered only when the goal declares `resultsSpanPages`. A page turn is classed like a click; only a real link named Next is read** | Without it, capabilities stop at whatever fits on one page, which a bank's histories never do. Bounded and with a declared exit, replay stays deterministic: same inputs, same pages turned, each logged. Several matching rows fail as ambiguous at once, running out fails saying how many pages were searched, and the goal, not the model, decides that results can span pages. |
| D29 | When drift across runs means "change the artifact" | (Pass 3 item 7) Each replay reports its own drift, but one fallback can be a slow page as easily as a renamed button. The AI recommended a report that reads the run logs, with a verdict per bank and step | **Agreed, acting only on a settled change: the last 3 runs on a bank all found the control by the same fallback (approve the override drift proposed), or all missed it, or kept switching fallbacks (re-record). Anything less is "watch". Only runs of the artifact's latest revision count, so an approved override starts afresh. The report only reads** | A single miss is often the input, not the bank: two members born the same day are `AMBIGUOUS_TARGET` by design. Advice to change an artifact that every run on that bank will follow should rest on a repeated observation. The revision hash keeps the report from re-raising drift that a person already fixed. Approving stays a person's act, as it is everywhere else. |
| D30 | How a calling agent reaches a capability | (Pass 3 item 8) The capability catalog was cut in D15; the user chose to build everything listed. The AI recommended an MCP server over the artifacts, not a new catalog format | **Agreed: `interface mcp` serves each approved artifact as one MCP tool. One server per bank: only artifacts whose allowlist holds that bank's origin are listed. The input schema is the artifact's inputs, the output is the result contract, and annotations say read-only or "stops before commit". The catalog is read from disk on every list and call; drafts are never offered. Unattended only** | The artifact already is a typed tool signature, so a catalog would only copy it. MCP is what agent hosts already speak. Scoping by origin keeps one bank's server from offering, or running, another bank's procedures. Reading from disk each time means withdrawing approval takes effect on the next call, with no cache to forget. An attended server (the D11 deadline and run handle as tool results) is the next step, not built. |
| D31 | A surface with no accessibility tree | (Pass 3 item 9) The user asked whether this works beyond the web, and chose to build a green screen: VT100 over a pseudo-terminal, with Claude discovering on it. The AI proposed building a tree from the characters, so the loop, recorder, masker, schema and replay are shared, not forked | **Agreed: `TerminalSurface` reads a 24x80 VT100 grid (pyte) over telnet-style TCP and builds the same snapshot: row 1 is the screen code and title, reverse-video runs are fields named by the caption before them, the key line's keys are buttons. Every target is scoped to its screen code. The last strategy is the grid position (`bbox` in character cells). The commit guard sits at the input: on a commitPaths screen only exit and cancel keys are sent** | A terminal grid doesn't move, so position is a real fallback here, not the guess it is on the web, and scoping to the screen code keeps it from ever landing on another screen. Building the tree from the screen keeps one discovery loop and one artifact format: what was learned about masking, identity and probes applies unchanged. The transport changed from the agreed local pseudo-terminal to telnet-style TCP, since real green-screen hosts are reached over the network; the emulator is the same. Not built: TN3270/5250 field attributes, and attended handoff on a terminal (the operator page is browser-based). |
